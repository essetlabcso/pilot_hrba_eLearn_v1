# CSO Learning Hub HRBA Course Design System

## 07 — Visual Asset Rules

## 1. Purpose

This document defines the visual asset rules for the CSO Learning Hub HRBA e-learning course.

Visual assets include:

* module cover images;
* course card images;
* scenario images;
* screen illustrations;
* hotspot scenes;
* diagrams;
* icons;
* completion visuals;
* thumbnails;
* downloadable worksheet previews;
* background textures or subtle decorative shapes.

The purpose of this file is to ensure that visual assets are consistent, premium, locally grounded, accessible, safe, and instructionally useful.

Coding agents must follow this file when adding, replacing, cropping, resizing, referencing, or implementing visual assets in the HRBA course.

This file builds on:

```text

docs/design-system/02_COURSE_PLAYER_SYSTEM.md
```

## 2. Core visual asset principle

Every visual asset must support learning.

A visual asset should do at least one of the following:

| Purpose       | Asset role                                                      |
| ------------- | --------------------------------------------------------------- |
| Orient        | Help learners understand where they are in the course/module    |
| Contextualize | Ground a scenario in realistic CSO practice                     |
| Clarify       | Make an abstract HRBA concept easier to understand              |
| Reveal        | Support hotspots, labels, or visual exploration                 |
| Compare       | Help learners see a difference between weak and strong practice |
| Guide         | Support a process, journey, or sequence                         |
| Motivate      | Create a warm, premium, confidence-building learning moment     |
| Complete      | Reinforce progress and achievement                              |

Visual assets must not be used as decoration only.

---

## 3. Approved visual style

The HRBA course visual system should feel:

* premium;
* warm;
* human-centered;
* Ethiopian or East African in context;
* respectful;
* practical;
* modern;
* visually clear;
* learning-platform ready;
* coherent across modules.

The visual style should not feel:

* generic corporate;
* generic Western stock-photo;
* overly donor-branded;
* poverty-framed;
* sensational;
* cluttered;
* childish;
* cartoonish unless explicitly approved;
* politically symbolic;
* legalistic or courtroom-based;
* disconnected from local CSO practice.

## 5. Module cover image rules

### 5.1 Purpose

Module cover images establish module identity and create a premium course experience.

They are used in:

* course catalogue cards;
* course overview page;
* enrolled course homepage;
* module start screens;
* possibly progress roadmap thumbnails.

### 5.2 Required style

Module cover images must be:

* 16:9 landscape;
* visually distinct by module;
* cohesive as one course series;
* cinematic or editorial in quality;
* human-centered where appropriate;
* rich but not cluttered;
* suitable for title overlay;
* free of readable embedded text;
* free of logos.

### 5.3 Required module visual directions

| Module                                         | Visual direction                                                                   |
| ---------------------------------------------- | ---------------------------------------------------------------------------------- |
| Module 1 — Starting the HRBA Learning Journey  | Pathway, opening doorway, guided journey, readiness, learning start                |
| Module 2 — Foundations of HRBA                 | Rights, actors, principles, power, dignity, interconnected relationships           |
| Module 3 — Applying HRBA in Project Design     | Co-creation, mapping, planning, project blueprint, stakeholder voice               |
| Module 4 — Applying HRBA During Implementation | Field action, participation, responsiveness, inclusion, accountability in practice |
| Module 5 — HRBA in MEAL                        | Evidence, feedback loops, learning, data use, accountability, adaptation           |
| Final Assessment                               | Synthesis, achievement, practical readiness, confident completion                  |

### 5.4 Avoid

Do not use:

* repeated workshop-table scenes;
* people only looking at laptops or papers;
* generic training-room photos;
* Western corporate office imagery;
* crowded group photos with no learning metaphor;
* images with readable text or logos;
* images that imply communities are passive recipients.

## 6. Scenario image rules

### 6.1 Purpose

Scenario images create context for realistic CSO decisions.

They should help learners feel:

```text
This could happen in practical CSO work.
```

### 6.2 Required style

Scenario images should be:

* realistic or semi-realistic;
* grounded in local CSO/community practice;
* respectful and non-stereotyped;
* clear enough to support the scenario;
* safe and fictionalized where needed;
* visually calmer than module covers.

### 6.3 Use scenario images for

| Scenario type                     | Image guidance                                      |
| --------------------------------- | --------------------------------------------------- |
| Community consultation            | Inclusive discussion setting, not tokenistic crowd  |
| Project planning                  | Co-creation, mapping, facilitation, community input |
| Field implementation              | Practical engagement, follow-up, outreach           |
| Feedback/accountability           | Listening, response, safe communication             |
| MEAL/data use                     | Evidence review, sensemaking, learning, adaptation  |
| Rights-holder/duty-bearer mapping | Actors in relation, not confrontation               |

### 6.4 Avoid

Do not use scenario images showing:

* real complaint documents;
* identifiable sensitive cases;
* distressing harm;
* political protest or partisan symbols;
* courtroom/legal-scale imagery;
* police/military confrontation unless explicitly required and safety-reviewed;
* stereotyped images of poverty or helplessness.

## 7. Hotspot scene rules

### 7.1 Purpose

Hotspot scenes are used when learners inspect a visual to identify hidden HRBA issues.

Examples:

* who may be excluded;
* where power appears;
* where voice is missing;
* what accountability channel is absent;
* what participation barrier exists;
* who has responsibility.

### 7.2 Required hotspot asset qualities

Hotspot images must:

* have clear composition;
* include enough visual anchors for hotspots;
* avoid clutter;
* avoid tiny detail;
* support 3–6 meaningful hotspots;
* work on desktop and mobile;
* include a text alternative;
* be fictional/generalized if sensitive.

### 7.3 Hotspot count

Recommended:

```text
Minimum: 3 hotspots
Ideal: 4–5 hotspots
Maximum: 6 hotspots
```

If more than 6 points are needed, split the screen or use an accordion/tabs alternative.

### 7.4 Required alternatives

Every hotspot scene must have:

* short alt text;
* long description;
* keyboard-accessible hotspot list;
* mobile list alternative.

## 8. Diagram rules

### 8.1 Purpose

Diagrams should make HRBA ideas practical and memorable.

Use diagrams for:

* HRBA lens;
* rights-holder/duty-bearer relationship;
* accountability loop;
* participation ladder/quality spectrum;
* project cycle;
* MEAL feedback loop;
* stakeholder ecosystem;
* safe data flow;
* inclusion barrier map.

### 8.2 Diagram style

Diagrams should be:

* simple;
* premium;
* clean;
* spacious;
* icon-supported where useful;
* color-token aligned;
* readable at course-player size;
* not overloaded with text.

### 8.3 Diagram text rules

Diagrams may include short labels only when necessary.

Avoid:

* long paragraphs inside diagrams;
* tiny labels;
* decorative arrows without meaning;
* too many colors;
* infographic clutter.

### 8.4 Accessibility

Every meaningful diagram must have:

* alt text;
* long description or text equivalent;
* keyboard-accessible version if interactive.

## 9. Icon rules

### 9.1 Icon purpose

Icons should help learners scan and remember concepts.

Use icons for:

* learning journey steps;
* HRBA principles;
* actor roles;
* progress status;
* completion status;
* tips and warnings;
* portfolio/tool markers;
* accessibility/resource markers.

### 9.2 Icon style

Icons must use:

* clean rounded line-and-soft-fill style;
* consistent stroke weight;
* simple forms;
* square composition;
* centered design;
* no embedded readable text;
* no logos;
* no flags;
* no political symbols;
* no legal scales;
* no courtroom imagery;
* no stereotypes.

### 9.3 Icon color palette

Use only approved token colors:

```text
Deep navy: #0F172A
Primary blue: #3B99D4
Soft green: #91C852
Warm gold: #D97706
Terracotta: #E45745
Warm neutral backgrounds where needed
```

### 9.4 Icon sizes

Use standard sizes from foundation tokens:

| Use                   | Size |
| --------------------- | ---: |
| Metadata icon         | 16px |
| Button/icon label     | 20px |
| Card icon             | 24px |
| Feature icon          | 32px |
| Learning journey icon | 48px |

## 10. Image cropping and layout rules

### 10.1 Cropping

Images must be cropped intentionally.

Do:

* preserve human dignity;
* preserve faces only where appropriate and safe;
* keep key visual action visible;
* maintain natural proportions;
* crop for composition, not convenience.

Do not:

* stretch images;
* distort aspect ratio;
* crop people awkwardly;
* crop out the important learning cue;
* create empty image areas that weaken screen balance.

### 10.2 Approved aspect ratios

| Asset use                  | Aspect ratio                               |
| -------------------------- | ------------------------------------------ |
| Module cover / course card | 16:9                                       |
| Hero side image            | 4:3 or 16:10                               |
| Scenario card image        | 4:3                                        |
| Hotspot scene              | 16:9 or 4:3                                |
| Icon                       | 1:1                                        |
| Diagram                    | 16:9, 4:3, or square depending on template |
| Completion visual          | 4:3 or square                              |

### 10.3 Image overlays

Use dark navy overlays only when text appears over images.

Recommended overlay:

```text
rgba(15, 23, 42, 0.72) at text side
fading to rgba(15, 23, 42, 0.20)
```

Do not place long text over busy images.

## 11. Asset naming rules

All visual assets must use deterministic names.

### 11.1 Naming structure

Use lowercase snake_case.

```text
[module]_[screen]_[asset_description]_v[number].[extension]
```

```text

m1_s05_water_point_scenario_v1.png
```

## 14. Asset assignment rules by screen

Every screen specification must identify assets clearly.

### 14.1 Required fields in screen specs

```md
### Visual assets
- File name:
- Path:
- Asset type:
- Purpose:
- Required alt text:
- Long description, if needed:
- Cropping instructions:
- Safety note:
```

### 14.2 If no asset is needed

Write:

```text
No visual asset required. Use layout, typography, and approved block styling only.
```

Do not insert decorative images just to fill space.

## 15. Alt text rules

### 15.1 Meaningful images

Meaningful images must have concise alt text.

Example:

```text
Illustration of local CSO staff and community members discussing a project plan together.
```

### 15.2 Decorative images

Decorative images should be marked as decorative in code.

Example:

```text
alt=""
aria-hidden="true"
```

### 15.3 Complex diagrams

Complex diagrams need a short alt text plus a long description.

Short alt example:

```text
Diagram showing the HRBA accountability loop.
```

Long description should explain the steps and relationships.

### 15.4 Hotspot scenes

Hotspot scenes must have:

* short alt text;
* long description;
* accessible hotspot list.

---

## 16. Visual safety rules

Visual assets must not expose people or organizations to risk.

### 16.1 Do not use images showing

* real complaint details;
* real safeguarding incidents;
* identifiable people in sensitive rights-related situations;
* political protest or partisan symbols;
* government confrontation;
* legal case documents;
* names, signatures, phone numbers, addresses, or IDs;
* children in sensitive or identifiable contexts without clear justification and safeguards;
* distressing images of harm;
* poverty-framed or pity-based imagery.

### 16.2 Use safer alternatives

Use:

* fictional illustrations;
* non-identifying scenes;
* symbolic visual metaphors;
* composite or staged learning scenes;
* diagrams instead of sensitive photos;
* blurred/non-readable document mockups where needed.

---

## 17. Local relevance rules

Assets should feel locally grounded without stereotyping.

Do:

* reflect Ethiopian/East African CSO contexts respectfully;
* show practical learning, dialogue, participation, field engagement, and collaboration;
* use warm human-centered scenes;
* show diversity of age, gender, ability, and community roles where relevant;
* represent local CSOs as capable actors.

Do not:

* use clichéd poverty imagery;
* overuse rural-only scenes if the topic applies broadly;
* show communities as passive recipients;
* use exaggerated smiles or staged stock-photo poses;
* use generic Western office imagery;
* use symbols that could be politically sensitive.

---

## 18. Asset quality rules

### 18.1 Minimum quality

Images should be:

* high resolution;
* sharp;
* well-composed;
* free of compression artifacts;
* free of unwanted text/logos;
* visually consistent with the course palette;
* usable in responsive layouts.

### 18.2 Recommended sizes

| Asset use         |                 Recommended size |
| ----------------- | -------------------------------: |
| Module cover      |                      1920 × 1080 |
| Course card       |                       1280 × 720 |
| Hero side image   |                       1200 × 900 |
| Scenario image    |                       1200 × 900 |
| Hotspot scene     |        1600 × 900 or 1400 × 1050 |
| Diagram           | SVG preferred or 1600px wide PNG |
| Icon              |                    SVG preferred |
| Completion visual |                       1200 × 900 |

### 18.3 File formats

| Format           | Use                                                  |
| ---------------- | ---------------------------------------------------- |
| `.svg`           | Icons, diagrams, simple vector assets                |
| `.png`           | Diagrams, transparent images, UI assets              |
| `.jpg` / `.jpeg` | Photographic images                                  |
| `.webp`          | Optimized web images where supported                 |
| `.pdf`           | Downloadable worksheets/resources, not screen images |

---

## 19. Performance and optimization rules

Assets should not slow the course unnecessarily.

Do:

* compress large images;
* use responsive image sizes where feasible;
* lazy-load non-critical images;
* avoid unnecessary animation files;
* use SVG for icons and simple diagrams;
* provide low-bandwidth alternatives for media-heavy screens.

Do not:

* use huge uncompressed images;
* load all module images at once;
* use animated backgrounds;
* use video where a static image or diagram would work better.

---

## 20. Asset replacement rules

When replacing an asset:

1. do not overwrite the old approved file;
2. create a new version number;
3. update the asset register;
4. update screen specs if the purpose changes;
5. update alt text if the visual meaning changes;
6. confirm safety and accessibility;
7. confirm responsive fit.

Example:

```text
m2_s20_power_lens_hotspot_scene_v1.png
m2_s20_power_lens_hotspot_scene_v2.png
```

Do not silently replace assets with different meaning.

## 23. Visual asset anti-patterns

Avoid these patterns.

| Anti-pattern                                     | Why it is a problem               |
| ------------------------------------------------ | --------------------------------- |
| Random decorative image                          | Does not support learning         |
| Same workshop scene repeated                     | Creates visual monotony           |
| People looking at papers/laptops on every module | Generic and repetitive            |
| Overly corporate stock image                     | Weak local relevance              |
| Poverty-framed imagery                           | Undermines dignity                |
| Political symbols                                | Safety and neutrality risk        |
| Legal scales/courtroom visuals                   | Too legalistic and cliché         |
| Text embedded in images                          | Translation/accessibility problem |
| Tiny diagram labels                              | Unreadable                        |
| Hotspot visual with too many points              | Cognitive overload                |
| Uncompressed large images                        | Performance problem               |
| No alt text                                      | Accessibility failure             |
| Replacing approved image without versioning      | Breaks asset traceability         |

## 24. Required implementation behavior for coding agents

Coding agents must:

1. use approved asset paths;
2. preserve file names;
3. preserve aspect ratio;
4. use approved cropping behavior;
5. add alt text for meaningful images;
6. mark decorative images correctly;
7. provide long descriptions for complex visuals;
8. implement hotspot text alternatives;
9. optimize image loading where feasible;
10. report missing assets instead of substituting random visuals.

Coding agents must not:

1. insert placeholder images unless explicitly instructed;
2. use external image URLs without approval;
3. rename approved assets without updating references;
4. distort or stretch images;
5. crop important learning cues;
6. use visual assets with logos or readable text;
7. use unsafe or identifiable images;
8. add decorative images to fill space;
9. replace approved images silently;
10. create new visual styles outside the design system.
