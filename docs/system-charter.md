# CSO Learning Hub AI-Assisted Learning Product System Charter

## Status

Draft v0.1 — Foundation governance document

## Purpose

The CSO Learning Hub is not only producing individual e-learning courses. It is building a reusable AI-assisted learning product development system for CSOs, using the HRBA e-learning course as the first pilot.

This charter defines the high-level governance, principles, boundaries, and pause-and-reflect rules for that system before screen production begins.

## Why This Charter Exists

The previous HRBA pilot had valuable content, visuals, and learning structure, but it also developed design drift because design-system thinking was introduced after screen production had already started.

This charter exists to prevent repeated layout patterns, accessibility patching, local CSS drift, unsafe contrast combinations, inconsistent icons, and AI improvisation.

## Core Working Principle

System first. Screens later.

Design rules before design production.

Learning purpose before interaction choice.

Accessibility from the start.

AI inside boundaries, not AI improvisation.

## What The System Must Combine

The CSO Learning Hub product system must combine four connected systems:

- Visual design system: colors, typography, spacing, layout, themes, components, responsiveness.
- Instructional design system: learning purposes, screen templates, interaction rhythm, practice, reflection, assessment.
- Accessibility system: readable contrast, keyboard support, screen reader support, read aloud, captions/transcripts, text size, reduce motion, glossary/plain language.
- AI production system: rules, prompts, approved schemas, QA gates, and boundaries for Codex and other AI tools.

## AI Boundaries

### Closed Areas

AI must not invent:

- brand foundations;
- color tokens;
- typography rules;
- spacing rules;
- button styles;
- component behavior;
- accessibility behavior;
- progress logic;
- locking/unlocking rules;
- certificate rules;
- mobile breakpoints;
- assessment scoring logic;
- navigation structure;
- file structure unless approved.

### Configurable Areas

AI may select from approved options:

- course theme packs;
- course player layouts;
- screen templates;
- learning block types;
- block variants;
- interaction types;
- feedback styles;
- content density levels;
- reflection formats;
- visual asset treatments.

### Generative Areas

AI may draft or propose:

- screen text;
- local CSO examples;
- scenarios;
- quiz questions;
- feedback;
- glossary definitions;
- read aloud scripts;
- accessibility metadata;
- image prompts;
- reflection questions;
- alternative explanations.

## Purpose-Driven Interaction Rule

No interaction should be used just because it looks interactive. Each interaction must come from learning purpose.

- Explain a concept → concept card, visual map, accordion.
- Compare ideas → comparison block.
- Apply judgment → scenario decision.
- Identify problems → risk-spotting block.
- Practice improvement → repair lab/tool practice.
- Reflect → guided journal or portfolio capture.
- Check understanding → knowledge check.
- Summarize → module synthesis.

## Controlled Variation Rule

We want certainty without sameness and variation without chaos.

Variation should come from approved theme packs, screen templates, block variants, layout modes, content density levels, and visual asset treatments — not from random local styling.

## Reuse Rule For The Old HRBA Pilot

- The old HRBA pilot is a protected legacy reference.
- Good content, module structure, images, visual direction, and learning ideas may be reviewed for migration.
- Old screen-level code, local CSS fixes, hard-coded colors, inconsistent icons, repeated layouts, and unsafe contrast combinations must not be copied directly.
- Assets/content can migrate only after review.
- Screen-level design debt must not migrate.

## Pause-And-Reflect Rule

Before making system or production decisions, pause and ask:

- Are we building the system, or drifting into screen-by-screen improvisation?
- Does this decision support predictable quality?
- Does it allow controlled variation?
- Are we defining the rule before building the example?
- Is AI operating inside clear boundaries?
- Are we solving a root system issue or only fixing a symptom?
- Will this make future courses easier or harder to build?
- Are accessibility and instructional design built in from the start?
- Do we need to define a missing template, block, or rule before coding?

## No Irreversible Change Principle

We cannot remove all risk, but we can prevent irreversible failure through:

- no destructive actions without review;
- branch and tag protection;
- no cleanup before preservation;
- no full rebuild before vertical slice;
- no AI improvisation;
- no unreviewed global style changes;
- build checks after technical steps;
- QA gates before scaling.
